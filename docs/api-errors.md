# API Error Format

Документ описывает единый формат ошибок backend API проекта BudgetWiseBackend.

Цель документа - зафиксировать структуру error response, чтобы frontend мог одинаково обрабатывать ошибки валидации, авторизации, доступа, конфликтов данных и внутренних ошибок сервера.

## Общий принцип

Все ошибки API должны возвращаться в едином формате.

Базовая структура:

```json
{
  "success": false,
  "error": {
    "status_code": 400,
    "code": "validation_error",
    "message": "Некорректные данные запроса.",
    "field_errors": {
      "field": [
        "Описание ошибки."
      ]
    },
    "detail": null,
    "trace_id": "optional-trace-id"
  }
}
```

## Назначение полей

| Поле | Тип | Обязательное | Описание |
|---|---|---|---|
| `success` | boolean | Да | Всегда `false` для ошибок |
| `error` | object | Да | Объект с деталями ошибки |
| `error.status_code` | integer | Да | HTTP-код ответа |
| `error.code` | string | Да | Машиночитаемый код ошибки |
| `error.message` | string | Да | Короткое понятное сообщение для пользователя или frontend |
| `error.field_errors` | object или null | Нет | Ошибки конкретных полей при валидации |
| `error.detail` | object, array, string или null | Нет | Дополнительная техническая информация |
| `error.trace_id` | string или null | Нет | Идентификатор ошибки для поиска в логах |

## Почему используется такой формат

Единый формат нужен, чтобы frontend мог:

- одинаково обрабатывать ошибки всех endpoints;
- показывать пользователю понятные сообщения;
- подсвечивать поля формы с ошибками;
- различать типы ошибок по `code`;
- передавать `trace_id` разработчику при обращении за поддержкой;
- не зависеть от разного формата ошибок Django, DRF, Simple JWT и бизнес-логики.

## Основные коды ошибок

| HTTP-код | `error.code` | Назначение |
|---|---|---|
| `400` | `validation_error` | Ошибка валидации входных данных |
| `400` | `bad_request` | Некорректный запрос |
| `401` | `authentication_failed` | Ошибка аутентификации |
| `401` | `not_authenticated` | Пользователь не авторизован |
| `403` | `permission_denied` | Недостаточно прав |
| `404` | `not_found` | Объект не найден |
| `405` | `method_not_allowed` | HTTP-метод не разрешён |
| `409` | `conflict` | Конфликт состояния данных |
| `500` | `server_error` | Внутренняя ошибка сервера |

## Ошибка валидации

Используется, когда входные данные не прошли проверку serializer, view или бизнес-правил.

Пример:

```json
{
  "success": false,
  "error": {
    "status_code": 400,
    "code": "validation_error",
    "message": "Некорректные данные запроса.",
    "field_errors": {
      "amount": [
        "Сумма должна быть больше нуля."
      ],
      "operation_date": [
        "Дата должна быть в формате YYYY-MM-DD."
      ]
    },
    "detail": null,
    "trace_id": null
  }
}
```

Frontend может использовать `field_errors` для подсветки конкретных полей формы.

## Ошибка авторизации

Используется, когда пользователь не передал JWT access token или передал некорректный token.

Пример:

```json
{
  "success": false,
  "error": {
    "status_code": 401,
    "code": "not_authenticated",
    "message": "Пользователь не авторизован.",
    "field_errors": null,
    "detail": {
      "detail": "Authentication credentials were not provided."
    },
    "trace_id": null
  }
}
```

## Ошибка доступа

Используется, когда пользователь авторизован, но не имеет прав на действие.

Пример:

```json
{
  "success": false,
  "error": {
    "status_code": 403,
    "code": "permission_denied",
    "message": "Недостаточно прав для выполнения действия.",
    "field_errors": null,
    "detail": {
      "detail": "You do not have permission to perform this action."
    },
    "trace_id": null
  }
}
```

## Объект не найден

Используется, когда запрашиваемый объект отсутствует или не принадлежит текущему пользователю.

Пример:

```json
{
  "success": false,
  "error": {
    "status_code": 404,
    "code": "not_found",
    "message": "Объект не найден.",
    "field_errors": null,
    "detail": {
      "detail": "Not found."
    },
    "trace_id": null
  }
}
```

Важно: если объект принадлежит другому пользователю, API также может возвращать `404`, чтобы не раскрывать факт существования чужого объекта.

## Конфликт состояния данных

Используется, когда запрос синтаксически корректен, но действие нельзя выполнить из-за текущего состояния данных.

Пример: попытка удалить категорию, которая используется в операциях.

```json
{
  "success": false,
  "error": {
    "status_code": 409,
    "code": "category_has_transactions",
    "message": "Категорию нельзя удалить, так как она используется в операциях.",
    "field_errors": null,
    "detail": {
      "category_id": 3
    },
    "trace_id": null
  }
}
```

Другие примеры конфликтов:

- удаление категории с дочерними категориями;
- удаление счёта, который используется в операциях;
- нарушение уникальности данных;
- попытка выполнить действие, запрещённое бизнес-правилом.

## Внутренняя ошибка сервера

Используется для непредвиденных ошибок.

Пример:

```json
{
  "success": false,
  "error": {
    "status_code": 500,
    "code": "server_error",
    "message": "Внутренняя ошибка сервера.",
    "field_errors": null,
    "detail": null,
    "trace_id": "6b1d9d5c-1d2a-4e55-9f8d-33c6c9f5f100"
  }
}
```

Для ошибки `500` frontend не должен показывать пользователю технические детали. Вместо этого можно показать общее сообщение и, при необходимости, `trace_id`.

## Trace ID

`trace_id` нужен для связи ответа API с записью в логах.

Правила:

- для обычных `400`, `401`, `403`, `404` `trace_id` может быть `null`;
- для критических ошибок и `500` `trace_id` должен быть заполнен;
- `trace_id` должен попадать в логи вместе с ошибкой;
- frontend может показывать `trace_id` пользователю как номер ошибки.

Пример сообщения для пользователя:

```text
Произошла внутренняя ошибка. Код обращения: 6b1d9d5c-1d2a-4e55-9f8d-33c6c9f5f100.
```

## Field errors

`field_errors` используется только для ошибок конкретных полей.

Пример:

```json
{
  "field_errors": {
    "email": [
      "Пользователь с таким email уже существует."
    ],
    "password": [
      "Пароль должен содержать не менее 8 символов."
    ]
  }
}
```

Если ошибка не относится к конкретному полю, используется поле `detail`.

Пример:

```json
{
  "success": false,
  "error": {
    "status_code": 400,
    "code": "business_rule_error",
    "message": "Нельзя деактивировать собственную учетную запись через этот endpoint.",
    "field_errors": null,
    "detail": {
      "reason": "self_deactivation_forbidden"
    },
    "trace_id": null
  }
}
```

## Требования к frontend

Frontend должен:

- проверять `success`;
- читать `error.status_code`;
- использовать `error.code` для выбора логики обработки;
- показывать `error.message` как основное сообщение;
- использовать `error.field_errors` для подсветки полей формы;
- не показывать пользователю технический `detail`, если он не предназначен для интерфейса;
- передавать `trace_id` разработчику при обращении за поддержкой.

## Требования к backend

Backend должен:

- возвращать ошибки только в едином формате;
- не отдавать пользователю traceback;
- не раскрывать лишнюю информацию о чужих объектах;
- использовать понятные `code`;
- логировать критические ошибки;
- добавлять `trace_id` для ошибок, которые нужно искать в логах;
- покрывать основные негативные сценарии автотестами.

## План реализации

Единый формат будет реализован в следующих подзадачах:

1. Ввести доменные классы ошибок.
2. Обновить глобальный exception handler.
3. Настроить нормализацию ошибок DRF, Django, Simple JWT и доменной логики.
4. Добавить подробное логирование критических ошибок.
5. Обновить API-контракт и OpenAPI-документацию.
6. Добавить автотесты негативных сценариев.

## Совместимость с текущей реализацией

На текущем этапе в проекте уже используется базовый единый формат:

```json
{
  "success": false,
  "error": {
    "status_code": 400,
    "detail": {
      "field": [
        "Error message"
      ]
    }
  }
}
```

В рамках BUD-24 формат будет расширен до целевого варианта с полями:

```text
code
message
field_errors
trace_id
```

Поле `detail` сохраняется для совместимости и дополнительной технической информации.
