# Monitoring Metrics

Документ описывает ключевые метрики мониторинга backend API проекта BudgetWiseBackend.

Цель документа - определить, какие показатели нужно собирать для оценки состояния системы, производительности API, стабильности базы данных и качества обработки ошибок.

## Общий подход

Мониторинг backend-части должен помогать быстро отвечать на вопросы:

- работает ли backend;
- доступна ли база данных;
- растёт ли количество ошибок;
- не ухудшилось ли время ответа API;
- нет ли проблем с авторизацией, валидацией или доступом;
- какие endpoints создают наибольшую нагрузку;
- есть ли признаки деградации системы.

Для проекта BudgetWiseBackend базовый мониторинг строится вокруг следующих групп:

1. HTTP/API метрики.
2. Метрики ошибок.
3. Метрики производительности.
4. Метрики базы данных.
5. Health-check метрики.
6. Системные метрики контейнеров.
7. Бизнес-метрики финансового модуля.

## Ключевые группы метрик

## 1. HTTP/API метрики

### `http_requests_total`

Тип: `counter`

Назначение: общее количество HTTP-запросов к backend API.

Рекомендуемые labels:

| Label | Описание |
|---|---|
| `method` | HTTP-метод: `GET`, `POST`, `PATCH`, `DELETE` |
| `path` | Шаблон маршрута или endpoint |
| `status_code` | HTTP-код ответа |
| `view` | Имя view или viewset, если доступно |

Пример:

```text
http_requests_total{method="GET",path="/api/v1/finance/categories/",status_code="200"} 152
```

Зачем нужна:

- считать RPS;
- видеть распределение запросов по endpoints;
- отслеживать рост 4xx и 5xx;
- понимать, какие части API используются чаще всего.

---

### `http_request_duration_seconds`

Тип: `histogram`

Назначение: время обработки HTTP-запросов.

Рекомендуемые labels:

| Label | Описание |
|---|---|
| `method` | HTTP-метод |
| `path` | Шаблон маршрута или endpoint |
| `status_code` | HTTP-код ответа |
| `view` | Имя view или viewset |

Пример:

```text
http_request_duration_seconds_bucket{method="GET",path="/api/v1/finance/transactions/",le="0.5"} 120
```

Зачем нужна:

- отслеживать latency API;
- считать p50, p95, p99;
- видеть медленные endpoints;
- находить деградацию после изменений в коде.

Целевой ориентир для dev/MVP:

| Показатель | Целевое значение |
|---|---|
| p95 для простых GET-запросов | до 500 мс |
| p95 для списков с фильтрацией | до 1000 мс |
| p95 для POST/PATCH операций | до 1000 мс |

---

### `http_requests_in_progress`

Тип: `gauge`

Назначение: количество HTTP-запросов, которые обрабатываются прямо сейчас.

Зачем нужна:

- видеть всплески параллельных запросов;
- отслеживать зависшие запросы;
- использовать как один из признаков перегрузки backend.

---

## 2. Метрики ошибок

### `api_errors_total`

Тип: `counter`

Назначение: количество ошибок API.

Рекомендуемые labels:

| Label | Описание |
|---|---|
| `status_code` | HTTP-код ошибки |
| `code` | Машиночитаемый код ошибки из error contract |
| `method` | HTTP-метод |
| `path` | Endpoint |
| `exception_type` | Тип исключения, если доступен |

Пример:

```text
api_errors_total{status_code="400",code="invalid",path="/api/v1/users/"} 12
```

Зачем нужна:

- отслеживать частоту ошибок;
- разделять клиентские ошибки `4xx` и серверные `5xx`;
- видеть, какие error codes встречаются чаще всего;
- строить alerts на рост `5xx`.

---

### `api_server_errors_total`

Тип: `counter`

Назначение: количество внутренних ошибок сервера `5xx`.

Рекомендуемые labels:

| Label | Описание |
|---|---|
| `path` | Endpoint |
| `exception_type` | Тип исключения |
| `code` | Код ошибки, обычно `server_error` |

Зачем нужна:

- быстро замечать падения backend;
- строить alert на любую серию `500`;
- связывать ошибки с логами через `trace_id`.

---

### `api_validation_errors_total`

Тип: `counter`

Назначение: количество ошибок валидации входных данных.

Рекомендуемые labels:

| Label | Описание |
|---|---|
| `path` | Endpoint |
| `field` | Поле, в котором произошла ошибка |
| `code` | Код ошибки, например `invalid`, `required`, `unique` |

Зачем нужна:

- видеть, какие поля чаще всего вызывают ошибки;
- помогать frontend улучшать формы;
- находить несовпадения между frontend и backend contract.

---

### `api_auth_errors_total`

Тип: `counter`

Назначение: количество ошибок аутентификации и авторизации.

Рекомендуемые labels:

| Label | Описание |
|---|---|
| `status_code` | `401` или `403` |
| `code` | `not_authenticated`, `authentication_failed`, `permission_denied` |
| `path` | Endpoint |

Зачем нужна:

- отслеживать проблемы с JWT;
- видеть частые запросы без токена;
- замечать попытки доступа к admin endpoints обычными пользователями.

---

## 3. Метрики производительности

### `api_response_size_bytes`

Тип: `histogram`

Назначение: размер HTTP-ответов.

Зачем нужна:

- находить слишком большие ответы;
- отслеживать endpoints, где нужна пагинация или оптимизация;
- контролировать нагрузку на сеть.

---

### `api_request_size_bytes`

Тип: `histogram`

Назначение: размер HTTP-запросов.

Зачем нужна:

- видеть слишком большие request body;
- отслеживать потенциально некорректные запросы;
- использовать для будущей защиты от злоупотреблений.

---

## 4. Метрики базы данных

### `database_up`

Тип: `gauge`

Назначение: доступность PostgreSQL.

Значения:

| Значение | Описание |
|---|---|
| `1` | База данных доступна |
| `0` | База данных недоступна |

Зачем нужна:

- быстро понимать, связана ли проблема backend с PostgreSQL;
- использовать в health-check;
- строить alert при недоступности базы.

---

### `database_check_duration_seconds`

Тип: `histogram`

Назначение: время проверки соединения с базой данных.

Зачем нужна:

- отслеживать деградацию соединения с PostgreSQL;
- видеть проблемы сети или контейнера базы;
- использовать в расширенном health-check.

---

### `database_queries_total`

Тип: `counter`

Назначение: количество SQL-запросов.

Рекомендуемые labels:

| Label | Описание |
|---|---|
| `operation` | `select`, `insert`, `update`, `delete`, если доступно |
| `status` | `success`, `error` |

Зачем нужна:

- оценивать нагрузку на базу;
- замечать резкий рост SQL-запросов;
- использовать при оптимизации endpoints.

На этапе MVP эта метрика может быть отложена, если её подключение усложняет код.

---

## 5. Health-check метрики

### `health_status`

Тип: `gauge`

Назначение: общий статус backend-сервиса.

Значения:

| Значение | Описание |
|---|---|
| `1` | Backend работает |
| `0` | Backend не работает или проверка завершилась ошибкой |

---

### `health_dependency_status`

Тип: `gauge`

Назначение: состояние зависимостей backend.

Рекомендуемые labels:

| Label | Описание |
|---|---|
| `dependency` | Название зависимости, например `postgresql`, `redis`, `external_api` |

Значения:

| Значение | Описание |
|---|---|
| `1` | Зависимость доступна |
| `0` | Зависимость недоступна |

На текущем этапе обязательная зависимость:

```text
postgresql
```

Планируемые зависимости на будущее:

```text
redis
celery
external_receipt_api
email_provider
```

---

## 6. Системные метрики контейнеров

Эти метрики обычно собираются не приложением Django, а инфраструктурой: Docker, node exporter, cAdvisor или аналогами.

Ключевые показатели:

| Метрика | Назначение |
|---|---|
| CPU usage | Нагрузка на процессор |
| Memory usage | Использование памяти |
| Disk usage | Использование диска |
| Network IO | Сетевой трафик |
| Container restarts | Перезапуски контейнеров |
| Container status | Состояние контейнеров |

Для docker-compose dev-окружения достаточно фиксировать эти метрики как планируемые для production.

---

## 7. Бизнес-метрики финансового модуля

Бизнес-метрики не должны содержать персональные финансовые данные пользователя. Они нужны только для оценки работы функций.

### `finance_transactions_total`

Тип: `counter`

Назначение: количество созданных операций.

Рекомендуемые labels:

| Label | Описание |
|---|---|
| `type` | `income` или `expense` |

Не нужно добавлять labels с `user_id`, суммой, описанием или названием категории.

---

### `finance_categories_total`

Тип: `gauge`

Назначение: количество категорий в системе.

Рекомендуемые labels:

| Label | Описание |
|---|---|
| `type` | `income` или `expense` |
| `is_active` | `true` или `false` |

---

### `finance_active_users_total`

Тип: `gauge`

Назначение: количество активных пользователей.

На этапе MVP эту метрику можно считать не в реальном времени, а через отдельную admin/statistics задачу в будущем.

---

## Минимальный набор метрик для MVP

Для текущего этапа проекта обязательными считаются:

| Метрика | Тип | Приоритет |
|---|---|---|
| `http_requests_total` | counter | Высокий |
| `http_request_duration_seconds` | histogram | Высокий |
| `api_errors_total` | counter | Высокий |
| `api_server_errors_total` | counter | Высокий |
| `database_up` | gauge | Высокий |
| `database_check_duration_seconds` | histogram | Средний |
| `health_status` | gauge | Средний |
| `health_dependency_status` | gauge | Средний |

Метрики бизнес-модуля можно добавить позже, после стабилизации CRUD для всех финансовых сущностей.

## Рекомендуемые dashboards

Минимальный dashboard должен показывать:

1. Backend availability.
2. RPS по API.
3. p95 latency по API.
4. Количество `4xx` и `5xx`.
5. Error rate.
6. Самые медленные endpoints.
7. PostgreSQL availability.
8. Время проверки PostgreSQL.
9. Количество запросов по ключевым endpoints.
10. Состояние контейнеров.

## Рекомендуемые alerts

Минимальные alerts:

| Alert | Условие | Критичность |
|---|---|---|
| BackendDown | `/health/` недоступен | Critical |
| DatabaseDown | `database_up == 0` | Critical |
| HighErrorRate | доля `5xx` выше порога | Critical |
| HighLatency | p95 latency выше порога | Warning |
| TooManyAuthErrors | резкий рост `401/403` | Warning |
| ContainerRestarting | backend или db контейнер часто перезапускается | Warning |

Точные пороги будут определены в задаче настройки alerting.

## Требования к безопасности

Метрики не должны содержать:

- email пользователя;
- username пользователя;
- описание операций;
- суммы операций конкретного пользователя;
- названия пользовательских счетов;
- названия пользовательских категорий;
- JWT token;
- password;
- refresh token;
- access token.

Допустимо использовать технические labels:

- HTTP method;
- endpoint path;
- status code;
- error code;
- exception type;
- dependency name.

## План реализации

1. Расширить health-check проверкой PostgreSQL.
2. Подключить endpoint `/metrics/` для Prometheus-compatible метрик.
3. Добавить middleware для сбора HTTP request count и latency.
4. Добавить счётчики ошибок в global exception handler.
5. Добавить метрики состояния базы данных.
6. Подготовить dashboard.
7. Подготовить alert rules.
8. Описать процедуру реагирования на alerts.
