# ADR 0010. Безопасность PWA push-подписок

## Статус

Принято.

## Контекст

PWA-клиент сохраняет push-подписки браузера на сервере. Подписка содержит технические ключи браузера `p256dh` и `auth`, а также endpoint push-сервиса. Эти данные не являются пользовательскими паролями, но позволяют серверу отправлять push-сообщения в конкретный браузер, поэтому API должен ограничивать доступ к подпискам текущим пользователем и не возвращать секретные части подписки в ответах.

## Решение

Для BUD-1134 приняты следующие правила:

- пользователь получает, отключает и тестирует только свои подписки;
- попытка обратиться к чужой подписке возвращает `404`, чтобы не раскрывать факт её существования;
- `DELETE` выполняет soft-delete: подписка остаётся в базе, но `is_active` становится `false`, заполняется `revoked_at`;
- повторная регистрация подписки с тем же endpoint для того же пользователя обновляет существующую запись;
- активные подписки ограничены настройкой `PWA_MAX_PUSH_SUBSCRIPTIONS_PER_USER`;
- `endpoint`, `deviceId`, `p256dh`, `auth` обязательны при регистрации;
- `endpoint` должен быть HTTPS URL;
- поддерживаемый провайдер на текущем этапе только `web_push`;
- `p256dh`, `auth` и полный `endpoint` не возвращаются в list/create response;
- приватный VAPID-ключ не возвращается в API и хранится только в `.env`.

## Последствия

Фронт может безопасно повторять регистрацию подписки после обновления Service Worker или браузерной подписки, не создавая дубли. Удалённые подписки можно оставить для аудита и диагностики, но они не используются для отправки push. Ограничение количества активных подписок защищает базу от неконтролируемого роста записей.
