# ADR 0006. Формат версионирования offline-first данных

## Статус

Принято.

## Контекст

После добавления API оффлайн-синхронизации фронту нужен единый формат версий данных. Этот формат должен позволять:

- определять, изменилась ли запись на сервере после последней синхронизации;
- безопасно повторять одну и ту же клиентскую мутацию без дублей;
- передавать серверную версию записи в IndexedDB;
- возвращать понятные конфликты для ручного разрешения;
- обрабатывать удаления через tombstone-записи.

## Решение

В MVP используется `timestamp_based`-подход. Серверной версией записи считается поле `updated_at`.

Формат версии записи:

```text
{resource}:{serverId}:{serverVersion}
```

Пример:

```text
transactions:15:2026-05-24T13:30:00+03:00
```

Для frontend-записи используется следующий набор полей:

```json
{
  "clientId": "local-uuid",
  "serverId": 15,
  "syncState": "synced",
  "baseVersion": "2026-05-24T13:00:00+03:00",
  "serverVersion": "2026-05-24T13:30:00+03:00",
  "clientUpdatedAt": "2026-05-24T13:20:00+03:00"
}
```

Для операций синхронизации используется:

```json
{
  "clientMutationId": "mutation-uuid",
  "baseSyncToken": "2026-05-24T13:00:00+03:00",
  "baseVersion": "2026-05-24T13:00:00+03:00",
  "clientUpdatedAt": "2026-05-24T13:20:00+03:00"
}
```

`clientMutationId` используется для идемпотентности. Повторная отправка той же операции возвращает сохранённый результат и не создаёт дубль.

`syncToken` является ISO datetime последней успешной серверной синхронизации. `pull` возвращает записи с `updated_at > since` и tombstone-записи с `deleted_at > since`.

## Конфликты

Для `update` и `delete` клиент передаёт `baseVersion`. Сервер сравнивает её с текущим `updated_at` объекта.

- если серверная версия не изменилась, операция применяется;
- если текущая серверная версия больше `baseVersion`, сервер возвращает `status=conflict`;
- в ответ конфликта включаются `clientData`, `serverData`, `baseVersion`, `serverVersion`, `conflictFields`, `availableStrategies`.

Доступные стратегии разрешения:

- `server_wins`, оставить серверную версию;
- `client_wins`, применить payload клиента;
- `merge`, применить вручную собранный payload.

## Удаления

Удаления не теряются после физического удаления записи. Для них используется `OfflineSyncTombstone`.

Ответ `pull` возвращает удаления в формате:

```json
{
  "id": "15",
  "deletedAt": "2026-05-24T13:30:00+03:00",
  "_sync": {
    "resource": "transactions",
    "serverId": "15",
    "serverVersion": "2026-05-24T13:30:00+03:00",
    "revision": "transactions:15:2026-05-24T13:30:00+03:00",
    "deleted": true
  }
}
```

## Почему не используются vector clocks

Векторные часы полезны для систем с несколькими независимыми узлами, где нет одного серверного источника истины. В текущем приложении сервер остаётся источником истины, а offline-first нужен для временной работы клиента без сети. Поэтому vector clocks усложнили бы реализацию и frontend-контракт без существенной пользы для MVP.

## Последствия

Плюсы:

- простой контракт для frontend и backend;
- понятное определение конфликтов;
- совместимость с текущими `updated_at` полями моделей;
- удобно объяснять в дипломной работе.

Минусы:

- нет автоматического сложного merge независимых изменений;
- при конфликте пользователь или frontend должен выбрать стратегию разрешения.
