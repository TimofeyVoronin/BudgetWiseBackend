# ADR 0008: Стратегии разрешения конфликтов offline-first синхронизации

## Статус

Принято.

## Контекст

В offline-first режиме пользователь может изменить данные без сети, а затем отправить batch изменений на сервер. За время отсутствия соединения та же запись может измениться на другом устройстве или через другой клиент. Сервер должен обнаружить конфликт и вернуть фронту данные, достаточные для безопасного разрешения без потери информации.

В проекте уже используется timestamp-based versioning: клиент отправляет `baseVersion`, сервер сравнивает её с текущим `serverVersion`, который строится на основе `updated_at`. Если серверная версия новее базовой версии клиента, возникает конфликт.

## Решение

Для MVP используются четыре стратегии:

1. `server_wins` - серверная версия остаётся источником истины, клиентский payload не применяется.
2. `client_wins` - клиентский payload принудительно применяется поверх серверной версии.
3. `merge` - фронт показывает пользователю `clientData`, `serverData` и `conflictFields`, затем отправляет итоговый payload после ручного выбора полей.
4. `last_write_wins` - сервер сравнивает `clientUpdatedAt` и текущий `serverVersion`. Более поздняя версия считается итоговой. Если клиентская версия новее, применяется payload клиента. Если серверная версия новее или `clientUpdatedAt` не передан, сохраняется серверная версия.

По умолчанию используется политика `manual_confirmation`: при конфликте сервер возвращает `status=conflict`, не изменяет запись и отдаёт фронту данные для ручного разрешения.

## API

Справочник стратегий:

```http
GET /api/v1/finance/sync/conflicts/meta/
```

Список нерешённых конфликтов:

```http
GET /api/v1/finance/sync/conflicts/
```

Разрешение конфликта:

```http
POST /api/v1/finance/sync/conflicts/resolve/
```

Пример запроса для ручного merge:

```json
{
  "resource": "transactions",
  "serverId": 15,
  "strategy": "merge",
  "payload": {
    "description": "Итоговое описание",
    "amount": "120.00"
  }
}
```

Пример запроса для `last_write_wins`:

```json
{
  "resource": "transactions",
  "serverId": 15,
  "strategy": "last_write_wins",
  "clientUpdatedAt": "2026-05-24T21:45:00+03:00",
  "payload": {
    "description": "Клиентская версия"
  }
}
```

## Последствия

Плюсы:

- фронт получает единый контракт для модального окна конфликтов;
- автоматические стратегии можно использовать для простых сценариев;
- ручной merge защищает от потери данных в спорных случаях;
- логика не требует vector clocks и остаётся понятной для дипломного проекта.

Минусы:

- `last_write_wins` зависит от корректности времени клиента;
- сложный merge коллекций, например вложенных `line_items`, остаётся ответственностью фронта и итогового payload;
- для полноценной истории конфликтов в будущем может понадобиться отдельная модель конфликтов, сейчас используется журнал `OfflineSyncOperation`.
