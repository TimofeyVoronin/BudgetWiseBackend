# ADR-0003: Подход к аутентификации и авторизации

## Статус

Принято

## Контекст

Backend предоставляет REST API для отдельного frontend-приложения. Пользовательские финансовые данные являются приватными, поэтому доступ к большинству API endpoints должен быть ограничен.

Требования к аутентификации:

- поддержка отдельного frontend-приложения;
- возможность передавать токен в HTTP-заголовке;
- отсутствие зависимости от серверных сессий для API;
- защита финансовых данных пользователя;
- возможность обновлять access token без повторного ввода логина и пароля.

## Решение

Для API выбрана JWT-аутентификация через Simple JWT.

В настройках Django REST Framework используется:

```python
REST_FRAMEWORK = {
    "DEFAULT_AUTHENTICATION_CLASSES": (
        "rest_framework_simplejwt.authentication.JWTAuthentication",
    ),
    "DEFAULT_PERMISSION_CLASSES": (
        "rest_framework.permissions.IsAuthenticated",
    ),
}
```

Это означает, что endpoints API по умолчанию закрыты для неавторизованных пользователей.

Для публичных endpoints используется `AllowAny`. Например:

- `/health/`;
- `/api/v1/`;
- будущие endpoints регистрации и получения токена.

Для проекта создана пользовательская модель на базе Django `AbstractUser`. Это решение принято на раннем этапе, до применения первых миграций, чтобы избежать проблем с заменой пользовательской модели в будущем.

На текущем этапе пользовательская модель содержит уникальный `email`, при этом `username` пока сохраняется для совместимости со стандартными механизмами Django.

Настройки Simple JWT задают короткий срок жизни access token и более длительный срок жизни refresh token. Access token используется для доступа к защищенным endpoints, refresh token используется для получения новой пары токенов без повторного ввода логина и пароля.

## Последствия

Преимущества решения:

- JWT хорошо подходит для REST API и SPA/PWA;
- frontend может передавать access token в заголовке `Authorization`;
- backend не зависит от серверных пользовательских сессий для API;
- Simple JWT поддерживает access и refresh tokens;
- custom User позволяет расширять пользовательскую модель без замены стандартного `auth.User` в будущем;
- закрытый по умолчанию API снижает риск случайного открытия приватных финансовых данных.

Ограничения решения:

- нужно внимательно работать с хранением токенов на frontend-стороне;
- refresh tokens требуют аккуратной настройки жизненного цикла;
- при необходимости полноценной email-аутентификации потребуется доработка логики входа;
- публичные endpoints нужно явно помечать через `AllowAny`.

## Альтернативы

Рассматривались следующие альтернативы:

1. **Session authentication**

   Session authentication хорошо подходит для классических Django-приложений, где frontend и backend находятся в одном приложении. Для отдельного frontend-приложения и REST API этот подход менее удобен, так как требует работы с cookies и CSRF.

2. **TokenAuthentication из Django REST Framework**

   TokenAuthentication проще JWT, но хуже подходит для сценария с access и refresh tokens. Для PWA удобнее использовать JWT-подход.

3. **OAuth2**

   OAuth2 подходит для сложных сценариев интеграции и сторонних клиентов. Для текущего MVP он избыточен, так как требует больше инфраструктуры и настроек.

## Итог

Для проекта выбрана JWT-аутентификация через Simple JWT. По умолчанию API закрыт для неавторизованных пользователей, а публичные endpoints явно помечаются через `AllowAny`.
