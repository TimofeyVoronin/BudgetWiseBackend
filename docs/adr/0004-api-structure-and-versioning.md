# ADR-0004: Структура API и версионирование

## Статус

Принято

## Контекст

Backend предоставляет REST API для отдельного frontend-приложения. API должен иметь понятную структуру маршрутов, поддерживать версионирование и быть готовым к расширению по мере развития финансового функционала.

Для проекта важны:

- единый префикс для API;
- возможность развивать API без нарушения совместимости;
- разделение маршрутов по логическим модулям;
- понятная структура endpoints для frontend-разработчика;
- единый подход к ошибкам;
- поддержка пагинации для списков;
- возможность автоматической генерации OpenAPI-документации.

На текущем этапе в проекте есть приложения:

- `common` - общие endpoints и служебные компоненты;
- `users` - пользователь, профиль, будущая регистрация и авторизация;
- `finance` - финансовые сущности: счета, категории, операции, бюджеты, цели.

## Решение

Для API выбрано версионирование через URL-префикс:

```text
/api/v1/
```

Основные маршруты проекта:

```text
/health/
/api/v1/
/api/v1/users/
/api/v1/finance/
/api/schema/
/api/docs/
```

Назначение маршрутов:

| URL | Назначение |
|---|---|
| `/health/` | Проверка состояния backend-сервиса |
| `/api/v1/` | Корневой endpoint API версии v1 |
| `/api/v1/users/` | Маршруты пользователей, профиля и авторизации |
| `/api/v1/finance/` | Маршруты финансового модуля |
| `/api/schema/` | OpenAPI-схема |
| `/api/docs/` | Swagger-документация API |

Файл `config/urls.py` отвечает за верхнеуровневую маршрутизацию:

```text
admin/
health/
api/v1/
api/schema/
api/docs/
```

Файл `config/api_urls.py` отвечает за маршруты версии API `v1`:

```text
users/
finance/
```

Маршруты отдельных приложений подключаются через собственные `urls.py`:

```text
apps/users/urls.py
apps/finance/urls.py
apps/common/urls.py
```

## Принципы версионирования

Для проекта выбран подход URL versioning.

Текущая версия API:

```text
v1
```

Если в будущем потребуется изменить контракт API несовместимым образом, новая версия может быть добавлена через отдельный префикс:

```text
/api/v2/
```

Примеры изменений, которые могут потребовать новой версии API:

- изменение структуры request или response;
- переименование ключевых полей;
- изменение формата ошибок;
- удаление существующих endpoints;
- изменение логики работы существующих endpoints, которое ломает совместимость с frontend.

Изменения, которые не требуют новой версии API:

- добавление новых endpoints;
- добавление необязательных полей в response;
- расширение фильтрации;
- добавление новых query-параметров без изменения старого поведения;
- исправление ошибок без изменения публичного контракта.

## Основные ресурсы API

Планируемая структура основных ресурсов:

```text
/api/v1/users/me/
/api/v1/auth/register/
/api/v1/auth/token/
/api/v1/auth/token/refresh/

/api/v1/finance/accounts/
/api/v1/finance/categories/
/api/v1/finance/transactions/
/api/v1/finance/budgets/
/api/v1/finance/goals/
/api/v1/finance/reports/
```

На текущем этапе маршруты `users` и `finance` подготовлены как точки расширения. Конкретные endpoints будут добавляться по мере реализации соответствующих задач.

## Формат ошибок

Для API используется единый обработчик ошибок Django REST Framework.

Базовый формат ошибки:

```json
{
  "success": false,
  "error": {
    "status_code": 400,
    "detail": {
      "field": [
        "Error message"
      ]
    }
  }
}
```

Такой формат позволяет frontend-приложению одинаково обрабатывать ошибки валидации, ошибки доступа и другие ошибки API.

## Права доступа

По умолчанию API закрыт для неавторизованных пользователей:

```python
"DEFAULT_PERMISSION_CLASSES": (
    "rest_framework.permissions.IsAuthenticated",
)
```

Публичные endpoints должны явно использовать `AllowAny`.

К публичным endpoints относятся:

```text
/health/
/api/v1/
```

В будущем к публичным endpoints также будут относиться:

```text
/api/v1/auth/register/
/api/v1/auth/token/
/api/v1/auth/token/refresh/
```

Остальные endpoints финансового модуля должны быть доступны только авторизованному пользователю.

## Пагинация

Для списков используется стандартная пагинация на базе `PageNumberPagination`.

Базовые настройки:

```text
page_size = 20
page_size_query_param = page_size
max_page_size = 100
```

Пагинация будет применяться для списков:

- счетов;
- категорий;
- операций;
- бюджетов;
- целей;
- отчетов и аналитических выборок, если они возвращают список записей.

## Фильтрация и сортировка

Фильтрация и сортировка будут добавляться на уровне конкретных ViewSet или APIView.

Для финансовых операций планируются фильтры:

- по счету;
- по категории;
- по типу операции;
- по периоду;
- по сумме;
- по признаку дохода или расхода.

Для списков также может использоваться сортировка:

- по дате создания;
- по дате операции;
- по сумме;
- по названию.

На текущем этапе правила фильтрации описаны как архитектурный ориентир. Реализация будет добавлена в задачах финансового модуля.

## OpenAPI-документация

Для документации API используется `drf-spectacular`.

Доступные маршруты:

```text
/api/schema/
/api/docs/
```

`/api/schema/` возвращает OpenAPI-схему.

`/api/docs/` предоставляет Swagger UI для просмотра и тестирования API.

## Последствия

Преимущества решения:

- API имеет понятную и предсказуемую структуру;
- frontend-разработчику проще ориентироваться в endpoints;
- URL versioning позволяет безопасно развивать API;
- маршруты разделены по приложениям;
- OpenAPI-документация может обновляться вместе с кодом;
- единый формат ошибок упрощает обработку ошибок на клиенте;
- базовая пагинация готова для будущих списков финансовых данных.

Ограничения решения:

- при большом росте API потребуется внимательно поддерживать структуру `finance`;
- часть правил фильтрации пока описана как будущая реализация;
- при появлении сложной аналитики могут потребоваться отдельные endpoints или отдельное приложение для отчетов.

## Альтернативы

Рассматривались следующие альтернативы:

1. **Версионирование через HTTP-заголовки**

   Такой подход позволяет не менять URL, но он менее очевиден для frontend-разработчика и сложнее для ручного тестирования через браузер или Swagger UI.

2. **Версионирование через query-параметр**

   Например, `/api/users/?version=1`. Такой подход хуже читается и может усложнить маршрутизацию.

3. **Отсутствие версионирования**

   Это проще на старте, но рискованно для развития проекта. Даже в дипломном MVP лучше сразу заложить понятную структуру версий.

## Итог

Для проекта выбрана структура API с префиксом `/api/v1/`. Маршруты разделены по логическим модулям `users` и `finance`, служебные endpoints вынесены отдельно, документация доступна через OpenAPI и Swagger UI. Такой подход подходит для текущего MVP и оставляет возможность безопасного расширения API в будущем.
