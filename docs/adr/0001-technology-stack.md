# ADR-0001: Выбор технологического стека backend-части

## Статус

Принято

## Контекст

Проект представляет собой backend-часть прогрессивного веб-приложения для управления личными финансами.

Серверная часть должна предоставлять REST API для frontend-приложения, хранить финансовые данные пользователей, поддерживать авторизацию, проверку прав доступа, работу с PostgreSQL и быть готовой к дальнейшему расширению.

Для проекта важны:

- понятная архитектура;
- быстрая разработка MVP;
- поддержка REST API;
- работа с PostgreSQL;
- возможность документировать API;
- удобная интеграция с отдельным frontend-приложением;
- пригодность выбранного стека для дипломного проекта.

## Решение

Для backend-части выбран следующий стек:

- Python 3.12;
- Django 5.2;
- Django REST Framework;
- PostgreSQL;
- Simple JWT;
- drf-spectacular;
- django-cors-headers;
- django-environ;
- Docker для локального запуска PostgreSQL.

Проект организован как модульный монолит. Основные приложения проекта:

- `users` - пользователи, профиль, будущая регистрация и авторизация;
- `finance` - финансовые сущности: счета, категории, операции, бюджеты, цели;
- `common` - общие компоненты: health-check, пагинация, обработка ошибок, утилиты.

Настройки разделены на окружения:

- `base.py` - общие настройки проекта;
- `dev.py` - настройки локальной разработки;
- `prod.py` - настройки production-окружения.

## Последствия

Преимущества решения:

- Django и Django REST Framework позволяют быстро создать стабильный REST API;
- PostgreSQL подходит для хранения связанных финансовых данных;
- Simple JWT подходит для отдельного frontend-приложения и PWA;
- drf-spectacular позволяет автоматически формировать OpenAPI-документацию;
- разделение настроек упрощает развитие проекта и будущий деплой;
- модульный монолит проще поддерживать на этапе MVP, чем микросервисную архитектуру.

Ограничения решения:

- Django-монолит требует аккуратного разделения логики по приложениям;
- часть production-инфраструктуры будет добавляться постепенно;
- Docker Compose пока не является основным способом запуска всего проекта, он будет подключен отдельной задачей.

## Альтернативы

Рассматривались следующие альтернативы:

1. **FastAPI**

   FastAPI хорошо подходит для async API и высоконагруженных сервисов. При этом для текущего дипломного MVP он требует больше самостоятельных решений по структуре проекта, админке, авторизации, миграциям и организации бизнес-логики.

2. **Flask**

   Flask гибкий и легковесный, но требует больше ручной настройки. Для проекта с пользователями, правами доступа, ORM, админкой и REST API Django дает более готовую основу.

3. **SQLite**

   SQLite подходит для простых локальных прототипов, но не является оптимальным выбором для финансового backend-приложения. Для проекта выбрана PostgreSQL, так как она лучше отражает реальные условия эксплуатации серверной части.

## Итог

Для проекта выбран стек Django + Django REST Framework + PostgreSQL. Это дает баланс между скоростью разработки, надежностью, понятной архитектурой и соответствием требованиям дипломного проекта.
