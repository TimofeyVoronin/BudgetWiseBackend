# BUD-1139. Требования к языку формул и UX редактора

## Назначение

Документ фиксирует минимальный backend-scope для задачи BUD-203 «API: Custom IDE For Financial Formulas».
Цель задачи - подготовить серверную основу для редактора финансовых формул: хранение черновика, получение состояния редактора, справочник переменных и функций, проверку DSL-кода, предпросмотр результата и согласованный формат ошибок для frontend.

Редактор формул на frontend отвечает за визуальное редактирование, подсветку синтаксиса, отображение подсказок и панель ошибок. Backend отвечает за хранение состояния, валидацию, безопасное выполнение поддерживаемого DSL и выдачу данных для предпросмотра.

## Зафиксированный MVP-scope

В рамках первой реализации используется один пользовательский черновик формулы:

```text
formula_id = draft-default
```

CRUD множества пользовательских формул на данном этапе не реализуется. Такой подход соответствует текущему frontend-контракту и снижает объём задачи.

Backend должен поддержать следующие возможности:

- получение сохранённого состояния редактора;
- сохранение черновика редактора;
- получение метаданных для палитры, переменных, операторов и автодополнения;
- проверка DSL-кода без выполнения формулы;
- предпросмотр результата формулы на финансовых данных пользователя;
- возврат ошибок DSL в формате, удобном для отображения в IDE;
- безопасное выполнение только разрешённых конструкций DSL.

## Базовый API-префикс

```text
/api/v1/finance/formulas/ide/
```

Все endpoints защищены JWT-аутентификацией.

## Endpoints

### Получение состояния редактора

```http
GET /api/v1/finance/formulas/ide/
```

Endpoint возвращает сохранённый черновик пользователя. Если черновик ещё не создавался, backend возвращает дефолтный пример формулы.

Минимальный ответ:

```json
{
  "formula_id": "draft-default",
  "code": "RETURN income - expense;",
  "constructor_blocks": [],
  "updated_at": "2026-06-13T10:00:00Z",
  "is_saved": true
}
```

### Сохранение черновика редактора

```http
PUT /api/v1/finance/formulas/ide/
```

Endpoint сохраняет код формулы и состояние конструктора блоков.

Минимальное тело запроса:

```json
{
  "code": "RETURN income - expense;",
  "constructor_blocks": [
    { "id": "b1", "kind": "function", "label": "SUM" }
  ]
}
```

Минимальный ответ:

```json
{
  "formula_id": "draft-default",
  "updated_at": "2026-06-13T10:05:00Z",
  "is_saved": true
}
```

Frontend перед сохранением вызывает validate. Если код невалиден, PUT не должен отправляться. Backend всё равно должен повторно проверить формулу на сервере, чтобы не сохранять заведомо некорректный DSL.

### Метаданные палитры и автодополнения

```http
GET /api/v1/finance/formulas/ide/meta/
```

Endpoint возвращает справочник для UI: группы переменных, функции, операторы, константы, элементы конструктора и автодополнения.

Справочник может быть статическим или полустатическим. Его можно кэшировать на стороне клиента.

Минимальный состав ответа:

- `variable_groups`;
- `constructor_variables`;
- `constructor_operators`;
- `autocomplete_items`.

### Валидация DSL

```http
POST /api/v1/finance/formulas/ide/validate/
```

Endpoint проверяет DSL-код и возвращает результат валидации без выполнения формулы.

Тело запроса:

```json
{
  "code": "RETURN income - expense;"
}
```

Ответ при валидной формуле:

```json
{
  "is_valid": true,
  "errors": []
}
```

Ответ при ошибках DSL:

```json
{
  "is_valid": false,
  "errors": [
    {
      "id": "unknown-variable",
      "line": 4,
      "message": "Неизвестная переменная budget.spent_rub.",
      "severity": "error"
    }
  ]
}
```

Требования к диагностике:

- `id` - стабильный идентификатор ошибки;
- `line` - номер строки, начиная с 1;
- `message` - человекочитаемый текст на русском языке;
- `severity` - `error` или `warning`;
- при `is_valid = false` массив `errors` не должен быть пустым.

### Предпросмотр выполнения формулы

```http
POST /api/v1/finance/formulas/ide/preview/
```

Endpoint проверяет формулу и выполняет поддерживаемый DSL на финансовых данных пользователя. Результат используется frontend для карточек результата и графика.

Тело запроса:

```json
{
  "code": "RETURN income - expense;",
  "constructor_blocks": []
}
```

`constructor_blocks` на первом этапе может сохраняться и возвращаться, но при выполнении preview backend может использовать только поле `code`.

Минимальный ответ:

```json
{
  "rows": [
    { "id": "income", "label": "Итого доход", "value": "125 400 ₽", "highlight": false },
    { "id": "expense", "label": "Итого расход", "value": "89 200 ₽", "highlight": false },
    { "id": "net", "label": "Чистый поток", "value": "36 200 ₽", "highlight": true }
  ],
  "chart_points": [
    { "month": "Янв", "value": 12 },
    { "month": "Фев", "value": 18 },
    { "month": "Мар", "value": 15 },
    { "month": "Апр", "value": 28 },
    { "month": "Май", "value": 22 },
    { "month": "Июн", "value": 36 }
  ]
}
```

Требования к preview:

- `value` в `rows` возвращается уже отформатированной строкой для UI;
- `highlight = true` используется для итоговой строки;
- `chart_points` содержит 6-12 точек;
- `month` содержит короткую подпись оси;
- вычисления выполняются только по данным текущего пользователя.

## Минимальный DSL

Для первой версии достаточно поддержать ограниченный DSL, который покрывает frontend-сценарий предпросмотра.

Рекомендуемый минимальный набор конструкций:

```text
LET <name> = <expression>;
RETURN <expression>;
```

Пример:

```text
LET income = SUM(TRANSACTIONS(type: INCOME, date: $period));
LET expense = SUM(TRANSACTIONS(type: EXPENSE, date: $period));
RETURN income - expense;
```

Допустимые переменные:

- `$period`;
- `$start_date`;
- `$end_date`;
- `$month`;
- `$year`;
- `$account`;
- `$accounts`;
- `$currency`;
- локальные переменные, объявленные через `LET`.

Допустимые константы:

- `INCOME`;
- `EXPENSE`;
- `TRANSFER`.

Допустимые функции для MVP:

- `TRANSACTIONS(...)`;
- `SUM(...)`;
- `AVG(...)`;
- `MIN(...)`;
- `MAX(...)`;
- `COUNT(...)`;
- `BALANCE(...)`;
- `ROUND(...)`;
- `IF(...)`.

Допустимые операторы:

- `+`;
- `-`;
- `*`;
- `/`;
- `==`;
- `!=`;
- `>`;
- `<`;
- `&&`;
- `||`.

Если какая-либо функция из справочника пока не реализована в исполнителе, backend должен вернуть понятную DSL-ошибку, а не падать с 500.

## Безопасность выполнения

Пользовательский DSL нельзя выполнять через `eval`, `exec` или произвольный Python-код.

Backend должен использовать безопасный разбор и исполнение:

- whitelist разрешённых функций;
- whitelist разрешённых операторов;
- whitelist разрешённых переменных;
- запрет `import`;
- запрет доступа к атрибутам объектов;
- запрет вызова произвольных функций;
- лимит длины `code`;
- лимит количества диагностик;
- безопасная обработка деления на ноль;
- изоляция данных по `user`.

Циклы, рекурсия и пользовательские функции в MVP не поддерживаются. Если такие конструкции будут переданы, backend должен вернуть DSL-ошибку.

## Формат ошибок

Для синтаксических и доменных ошибок DSL используется HTTP 422.

Рекомендуемый формат ответа:

```json
{
  "detail": "В формуле найдены ошибки",
  "errors": [
    {
      "id": "unknown-variable",
      "line": 4,
      "message": "Неизвестная переменная budget.spent_rub.",
      "severity": "error"
    }
  ],
  "error": {
    "code": "FORMULA_VALIDATION_FAILED",
    "message": "В формуле найдены ошибки",
    "errors": [
      {
        "id": "unknown-variable",
        "line": 4,
        "message": "Неизвестная переменная budget.spent_rub.",
        "severity": "error"
      }
    ]
  }
}
```

Ошибки дублируются на верхнем уровне и внутри `error`, чтобы frontend мог стабильно читать их из разных форматов.

Для некорректного JSON/body используется общий формат ошибки проекта с HTTP 400.

Для отсутствующего или просроченного токена используется HTTP 401.

## Граничные случаи

Backend должен обрабатывать следующие ситуации:

- пустой `code`;
- слишком длинный `code`;
- отсутствующий `RETURN`;
- неизвестная переменная;
- неизвестная функция;
- незакрытая скобка;
- некорректный `LET`;
- деление на ноль;
- пустая история операций пользователя;
- unsupported DSL-конструкция;
- ошибка выполнения preview;
- попытка получить или изменить чужой черновик.

## Что не входит в MVP

В первую реализацию не входят:

- CRUD множества сохранённых формул;
- публикация формул в отчёты;
- запуск формул внутри combined/comparative/forecast analytics;
- пользовательские функции;
- циклы и рекурсия;
- AI-генерация формул;
- полноценный zero-knowledge режим для формул;
- синхронизация зашифрованных envelope-полей.

Блок локального шифрования из frontend-контракта относится к security/sync-задачам и не должен смешиваться с BUD-203.

## Acceptance criteria

BUD-1139 считается выполненной, если:

- зафиксирован MVP-scope формульного редактора;
- определён список backend endpoints;
- определён минимальный DSL;
- зафиксированы правила диагностики ошибок;
- описаны ограничения безопасности;
- явно указано, что CRUD множества формул и интеграция с отчётами не входят в первый этап;
- следующий шаг BUD-1140 может начинаться без дополнительных уточнений по общему scope.

- BUD-1147 - оптимизация;
- BUD-1148 - тестирование;
- BUD-1149 - документация языка и API;
